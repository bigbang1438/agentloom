# Agent 工具调用的安全边界

## 为什么模型输出不可信

大模型的工具调用（Function Calling）输出，本质上和用户输入一样不可信。
原因有三条：

1. **参数是模型生成的**。模型可能给出类型错误的参数、缺少必填项、
   或者塞进 schema 里根本没声明的字段。
2. **模型会被上下文带偏**。检索到的文档、工具返回的内容里如果藏着
   「忽略之前的指令」这类文本，模型可能把它当成新指令执行。
3. **模型的「批准」没有意义**。如果模型手里有一个「审批」工具，
   它完全可以自己调用自己批准。审批权必须留在人手里。

## 四道校验

工具调用进入执行前，必须通过：

1. **工具白名单**。不在白名单里的工具名直接拒绝，防止模型臆造工具。
2. **参数必须是 JSON 对象**。字符串、数组、null 都不接受。
3. **未声明字段一律拒绝**。这是防参数走私的关键，对应 JSON Schema 的
   `additionalProperties: false`。典型攻击是往查询接口里塞 `approved: true`。
4. **逐项校验**。必填、类型、枚举、长度上限、数值范围。

校验失败**不抛异常**，而是转成一条「拒绝观察结果」回灌给模型，
让它知道错在哪、换个做法。这样既守住边界，又不牺牲可用性。

## 预算控制

Agent 必须有预算，否则会无限自问自答。五个维度：

| 维度 | 作用 |
| --- | --- |
| 模型轮次 | 限制模型被调用的次数 |
| 工具调用次数 | 限制工具执行总数 |
| 总步数 | 模型轮次 + 工具调用的合计上限 |
| 墙钟超时 | 整体时间上限 |
| token 与成本 | 防止单次请求烧掉过多额度 |

超预算**不返回 500**，而是返回结构化的 `stopped_reason`。
调用方据此区分「被截断」和「失败」——前者可以放宽预算重试，后者要排查。

## 人工确认

写操作（创建任务、修改数据、发送消息）必须过人工确认：

- 模型只能**提出**确认请求，拿不到审批工具。
- 确认编号由服务端生成，绑定具体参数与会话。
- 每个确认编号只能被消费一次，重复提交返回冲突。
- 没有配置审批人时，写操作**默认拒绝**（安全默认）。

## 引用校验

知识问答必须带来源。规则：

- 引用编号由**服务端分配**，模型只能引用已分配的编号。
- 答案里出现未分配的编号时，该结论被拦截。
- 检索无结果时强制拒答，不允许凭记忆编造。

边界说明：编号合法**只证明指向了真实片段**，不证明每句话都被该片段支持。
语义层面的支持需要人工或额外的模型复核，这里不假装做到了。
